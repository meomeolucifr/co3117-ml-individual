1. Purpose, Learning Outcomes, and Assessment Philosophy

This assignment converts the traditional multi-model project into an individual, longitudinal learning system. Students repeatedly revisit the same prediction task with the model families in the CO3117 syllabus. The primary goal is not leaderboard optimization or metric chasing; the goal is to connect mathematical formulation, algorithmic steps, implementation choices, empirical behavior, and written explanation.

  • Explain core ML concepts, assumptions, objectives, update rules, inference procedures, and model limitations in concise, rigorous written form.
  • Implement selected core mechanisms from scratch in NumPy/Python (Depth A) and validate them numerically against trusted references.
  • Read reference code critically (Depth B), mapping equations and algorithm steps to concrete code paths.
  • Compare model families under a common split, preprocessing protocol, primary metric, and held-out test population.
  • Build a cumulative, inspectable learning record through prospective Git commits, a wiki/blog knowledge base, weekly exercises, and two graded submission milestones.
  • Demonstrate individual ownership: the student must be able to derive, locate, explain, test, modify, and defend any submitted component on demand.

1.1 Alignment with the CO3117 Syllabus and Written Final Exam

The CO3117 syllabus emphasizes understanding fundamental concepts, deriving mathematical foundations and training mechanisms of representative models, comparing strengths and limitations, applying appropriate algorithms, performing dimensionality reduction, and evaluating models in realistic settings.

The sample 90-minute final exam (code 504, 26 May 2026) uses short constructed-response questions rather than programming. It tests conceptual definitions, comparisons, conditional independence in Bayesian networks, PCA derivation, AdaBoost weight updates, generative versus discriminative modeling, and SVM margin reasoning. This assignment therefore establishes an integrated written-exam track alongside coding and controlled experiments.

⚠️ Pedagogical Principle
The assignment develops practical implementation ownership and written theoretical fluency simultaneously. Code alone is not sufficient; prose alone is not sufficient. You must be able to derive what you code, and explain without code what your models compute.

2. Non-Negotiable Rule: One Dataset, One Use Case

🔒 Mandatory Invariant Rule
The dataset source and version, prediction target, decision context, and held-out test population remain fixed for the entire semester. Different feature representations of the SAME raw data are encouraged; switching to a second dataset merely to accommodate a particular model is strictly prohibited.
  • Freeze Protocol: Finalize the dataset source, target label, split policy, primary metric, and random seeds by the end of the Course Week 5 release checkpoint (R0), before Week 6 begins. Document this in protocol.yaml.
  • Pre-processing Hygiene: Fit all scalers, encoders, PCA/LDA projections, and feature selectors on training data only; then transform validation and test sets.
  • Sealed Test Set: Keep the final test partition sealed until cross-model comparison; all hyperparameter tuning occurs strictly on training/validation folds.
  • Sequential Views: For sequential models (HMM/CRF), derive an ordered, temporally continuous view from the same underlying dataset and document the derivation.
  • Model Suitability Study: If a syllabus model is genuinely mismatched with your fixed prediction task, submit a rigorous Model Suitability Study explaining the theoretical mismatch rather than forcing a scientifically meaningless run.

2.1 Canonical Use Case and Approved Alternatives

  • Canonical Dataset: UCI Human Activity Recognition Using Smartphones (UCI HAR). The stable task is: predict a user’s current physical activity from smartphone inertial sensor measurements. For HMM/CRF, temporal continuity is exploited to smooth or decode activity sequences over time.
  • Structural Exemplar: The prior-cohort report “Detect AI Generated Text” serves as a structural and architectural exemplar for assembling a theory → code → experiment → reflection dossier. It is not an answer key. Students must not copy its text, code, tables, or results. If text detection is approved as a custom use case, a single dataset must be frozen and any sequence transformation justified explicitly.

4.1 Implementation-Depth Classification

Depth Level Meaning Minimum Verifiable Evidence
Depth A — BUILD Author the core algorithm yourself in NumPy/Python without high-level estimator libraries. Mathematical derivation; clean NumPy code; unit tests against synthetic cases; pre-reference and post-reference commits.
Depth B — DISSECT & MODIFY Study an approved reference implementation, explain its architecture, and execute a non-trivial adaptation. Exact code attribution; line-by-line mapping; meaningful diff; controlled experiment demonstrating effect of modification.
Depth C — APPLY & BENCHMARK Use an approved reference library to evaluate applicability, parameter sensitivity, and limits. Justified hyperparameters; controlled benchmark; confusion matrix; comprehensive error/limitation analysis.

6. Weekly Wiki/Blog Post: The Living Knowledge Dossier

Submit one combined 500–900 word PRE-RELEASE catch-up post for W01–W04, then one concise 350–700 word post for each ordinary week W05–W07 and W09–W15. Week 8 requires only a compact midterm reflection.

  1. A. Concept Capsule: Mathematical definition, probabilistic assumptions, hypothesis space, objective function, and failure modes.
  2. B. One Derivation or Worked Example: A step-by-step mathematical proof, numeric calculation, d-separation analysis, or gradient derivation.
  3. C. Code-to-Theory Trace: Map 2–4 mathematical equations to exact function and line numbers in your own code and cited reference code.
  4. D. One Controlled Experiment: Focus on one clear experimental variable (learning rate, depth, smoothing parameter, regularization strength CC).
  5. E. Failure & Misconception Analysis: One empirical failure case, edge-case vulnerability, or conceptual misunderstanding analyzed in depth.
  6. F. Written-Exam Capsule: 4–8 sentences explaining the week’s core theoretical concept concisely without referencing code.
  7. G. Reflection: Concrete statement of what is now understood that was previously unclear, and what remains uncertain.
  8. H. Inquiry Trail (Mandatory when AI is used): Question asked, pre-AI attempt hash, AI suggestion summarized, textbook/MOOC verification source, and what can now be reproduced independently.

12. Academic Integrity & AI-Assisted Inquiry-Based Learning (IBL) Protocol

AI assistants and external repositories may support learning only when they stimulate independent questioning, hypothesis formulation, and rigorous derivation. Productive struggle must always precede tool consultation.

0. FRAME      Write learning question and initial hypothesis before opening AI.
    ↓
1. ATTEMPT    Solve/derive/code independently. Commit raw attempt to Git history.
    ↓
2. INQUIRE    Ask AI for ONE Socratic hint, diagnostic question, or counterexample at a time.
    ↓
3. VERIFY     Cross-check AI responses against lecture notes, Murphy, or Ravindran MOOC.
    ↓
4. RECONSTRUCT Close AI window. Re-derive or re-code from memory in your own structure.
    ↓
5. TRANSFER   Solve a parameter variation or edge case not present in the original prompt.
    ↓
6. TEACH-BACK Explain the concept concisely as if teaching a peer (exam capsule).
    ↓
7. RETRIEVAL  Reproduce key derivation after 24–72 hours closed-book.
  • Prohibited Uses: Generating first-attempt drills, pasting AI code into Depth-A components, generating synthetic weekly posts, or disguising external solutions.
  • Disclosure: Every AI interaction is recorded in AI_USE.md (Date, Learning Question, Pre-AI Commit, AI Tool, Prompt Purpose, Hint Summary, Verification Source, Closed-Book Status).
